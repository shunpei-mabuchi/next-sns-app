# MVP定義

本ドキュメントは、PiBitの必須実装MVPの範囲と完成条件を定義する。requirements.mdはアプリ全体の要件を扱い、MVPで実装する機能の具体的な採否と完成条件は本ドキュメントを基準とする。
対象外とした機能も、既存の要件・画面・ルーティング設計からは削除せず、将来仕様として維持する。実装時期・実装有無は別途判断する。
本ドキュメントに画面・ルートが記載されていても、実装完了を意味しない。

---

## 1. MVPの目的

- 最優先の目的は、Next.js・NestJS・Prisma・MySQL を使ったフルスタック開発を理解すること
- UI デザインの完成度よりも、次の理解を重視する
  - ルーティング
  - フォーム
  - REST API
  - 認証・認可
  - DB 設計・リレーション
  - CRUD

## 3. 各機能の完成条件

### 認証

- 新規登録でアカウントを作成でき、公開ユーザーIDが自動生成される（一意・変更不可）
- 入力値のバリデーション（メール形式、パスワードの長さ・複雑さ等）がバックエンドで行われる
- 既存のメールアドレスでは登録できず、誤ったパスワードではログインできない
- ログイン・ログアウトができ、ログイン状態がリロード後も維持される
- 設定画面 `/settings` を最低限実装する（ログアウトの導線を持つ）
- ログアウトは確認モーダルを表示し、実行後は認証状態を破棄してログイン画面へ遷移する
- パスワード変更・アカウント削除の実処理や、その他の設定画面の詳細機能は対象外とする（「4. MVP対象外」参照）
- 未ログインで保護された画面へアクセスすると、戻り先を `callbackUrl` として保持して `/login` へリダイレクトする
- ログイン成功後、検証済みの内部相対パスである `callbackUrl` があればその画面へ戻り、存在しない・不正な場合はCanvas（`/`）へ遷移する。外部サイトへのリダイレクトを許可しない
- ログイン済みで `/login` `/signup` へアクセスすると `/` へリダイレクトされる
- 認証・認可は NestJS API 側でも検証される
- パスワードの平文保存を行わず、パスワードハッシュ等の機密情報をAPIレスポンスに含めない。具体的なハッシュ方式・認証方式・Cookie管理は未確定
- 不正入力、未認証、権限不足、対象なし、重複、予期しない内部エラーに対して、requirements.mdのHTTPステータス方針に沿った応答を返す。具体的なレスポンス形式はAPI設計時に決める

### 投稿

- 投稿を作成でき、空の投稿・文字数超過はエラーになる
- 投稿作成の成功後は、モーダルを閉じて元の画面に反映される（ホームへ固定遷移しない）
- タイムラインに投稿が新しい順で表示される
- 投稿詳細を表示でき、存在しない投稿は 404 になる
- 自分の投稿・リプライのみ削除でき、削除前に確認モーダルを表示する。他ユーザーの投稿は API 側でも削除を拒否する
- ホームでリプライを選択すると投稿詳細へ遷移し、投稿詳細内でリプライを作成・表示できる
- リポストと解除ができ、同じ投稿への重複リポストは防止される

### 交流

- いいねと解除ができ、同じ投稿への重複いいねは防止される
- フォローと解除ができ、重複フォローは防止される
- リポストと解除ができ、重複リポストは防止される
- いいね・リポストは画面遷移せず、同一画面内で完結する

### プロフィール

- マイページに自分のプロフィールと、投稿・リプライ・いいね・リポストのタブが表示される
- 他ユーザープロフィールに、プロフィールとフォロー・フォロー解除、各タブが表示される。存在しない公開IDは 404
- 自分自身の公開IDで `/users/[userId]` にアクセスすると `/mypage` へリダイレクトされる
- プロフィールを編集して保存でき、未保存の変更がある状態でキャンセルすると変更破棄確認モーダルが表示される
- MVPでは表示名・プロフィール文・生年月日・公開設定などのテキスト情報を編集する。プロフィール画像・ヘッダー画像の変更処理は対象外
- `/mypage/follows` は自分のフォロー・フォロワー一覧を表示する画面で、フォロー / フォロワーのタブを切り替えられ、ユーザー選択で他ユーザープロフィールへ遷移できる
- マイページのフォロー数・フォロワー数は選択可能で、フォロー数は `/mypage/follows?tab=following`、フォロワー数は `/mypage/follows?tab=followers` へ遷移する
- 他ユーザープロフィールにもフォロー数・フォロワー数を表示するが、選択はできない。他ユーザーのフォロー・フォロワー一覧画面は追加しない
- タブの選択状態は `tab` クエリパラメータで管理され、不正な値の場合は初期タブを表示する

### 検索

- 公開ユーザーID・表示名でユーザーを検索でき、結果の選択で他ユーザープロフィールへ遷移できる
- 投稿本文で投稿を検索でき、結果の選択で投稿詳細へ遷移できる
- 検索は部分一致で実装する

### 通知

- いいね・リプライ・リポスト・フォローの通知が新しい順に一覧表示される
- 未読件数が管理でき、フッターの通知に未読バッジを表示できる

## 4. MVP対象外

| 対象外 | 補足 |
|---|---|
| 管理者機能全般 | 管理者側のルート・画面は設計から削除しない |
| センシティブ投稿の自動検出 | 候補の選定方法は未決定のまま |
| 高度な検索 | 人気順などは対象外 |
| リアルタイム通知 | 通知自体は必須 |
| Pieceへの画像添付 | 投稿作成モーダルの画像添付UI設計は維持する |
| プロフィール画像・ヘッダー画像の変更処理 | 画面要件・将来仕様として維持する |
| UI アニメーション・細かなデザイン調整 | shadcn/ui + Tailwind CSS で最低限の見た目に留める |
| パスワード再設定 | 画面・ルートは将来仕様として残す。画面・実処理ともMVPには含めない |
| パスワード変更の実処理 | パスワード変更モーダルの設計は残す |
| アカウント削除の実処理 | アカウント削除確認モーダルの設計は残す |
| 設定画面のその他の詳細機能 | 後工程で検討する。ログアウトと `/settings` の最低限の実装は必須 |

Inbox・ユーザー検索・投稿検索はMVP対象だが、実装優先順位は後工程とする。「優先順位が後工程」であることは、MVP対象外を意味しない。

## 5. 使用技術と学習目標

| 技術 | 用途 | 学習目標・現状 |
|---|---|---|
| Next.js（App Router） | フロントエンド | ルーティング、Route Group、レイアウト、フォーム、保護ルート |
| NestJS | バックエンド（REST API） | 基礎環境構築済み。一部機能APIを実装中で、認証機能は未実装。API設計、入力検証、認証・認可、責務分離を学ぶ |
| Prisma | ORM | 採用予定・未実装。スキーマ定義、リレーション、マイグレーション、CRUDを学ぶ |
| MySQL | DB | 採用予定・未実装。DB設計、リレーション、重複防止（いいね・フォロー等）を学ぶ |
| shadcn/ui + Tailwind CSS v4 | UI | 最低限の見た目の実装。プロジェクト内のUIコンポーネントを利用（旧: MUI / Emotion、削除済み） |
| Lucide Icons | アイコン | ヘッダー・フッターなどのアイコン表示 |

## 6. フロント・バックエンドの段階的な並行開発方針

フロントエンドとバックエンドは一方をすべて完成させてから他方を始めるのではなく、基礎学習・実装を並行して進め、機能単位で段階的に連携する。

1. Next.js側では画面で扱うデータの型を先に検討する
2. 型に対応したモックデータを用意し、モックデータで画面表示を確認する
3. React コンポーネントは開発者本人が実装する。モックデータの生成に限り、[AGENTS.md](../AGENTS.md) のルールに従って AI を利用できる
4. NestJS側ではAPIの学習・実装を並行して進める。Prisma・MySQLの採用予定は、実装済みを意味しない
5. 機能単位でNestJS APIが利用可能になった時点で、該当機能のモック取得処理をAPI通信へ切り替える
6. 画面・コンポーネントとデータ取得処理の責務を分離し、モックからAPIへの切り替え範囲を明確にする
7. モックデータの設計方針
   - モックデータは画面コンポーネントに直接埋め込まず、分離して管理する
   - TypeScript でデータ型を定義し、将来の NestJS API レスポンスを意識したデータ構造にする
   - データ取得処理と UI コンポーネントの責務を分離する
   - API 連携時は、モックの取得処理を実際の API 通信へ置き換える
   - API のレスポンス形式や型の詳細は、API 設計時に確定する
   - 目的は、NestJS API へ切り替える際の修正範囲を小さくすること
8. モック段階の認証状態や権限チェックは仮実装であり、実際のセキュリティを保証するものではない
9. 認証・認可・入力検証はバックエンドで行う（フロントの検証は補助）
10. shadcn/ui + Tailwind CSS は最低限の見た目に使用し、Figma での詳細な UI 設計は行わない

## 7. MVP全体の完成判定

以下をすべて満たした段階で MVP 完了とする。

- 「3. 各機能の完成条件」をすべて満たしている
- MVPの各機能についてモックによる画面確認を行い、最終的にNestJS APIをNext.jsから呼び出して動作する
- 認証・認可・入力検証がバックエンドで行われている
- 画面遷移・URL が screen-flow.md / routing.md と一致している
- 異常系（空の投稿、重複登録、重複いいね・フォロー・リポスト、404、権限なし）が適切に扱われる
- テストが最低限実施できる
